# nisa-buy-timing 仕様(v0.1)

NISA の成長投資枠で投資信託を買うときの「買い時」を、過去データに基づく参考指標で示す PWA。
スマホのホーム画面に追加して使う。GitHub Pages(public)で配信し、データの更新と通知は GitHub Actions が受け持つ。

## 0. 前提と非目的

- 将来の値動きは当てられない。アプリが示すのは「その投信が、過去の自分自身と比べてどれだけ安い局面か」と、その指標が過去に役立ったかの検証結果。断定的な表現(「今が底」「必ず上がる」)を画面と通知に出さない。
- 投資助言ではない。注文は行わない。SBI 証券や運用会社とは無関係の個人ツールであり、ロゴや名称を公式のように使わない。
- 注文締切、約定日、受渡日、年内受渡の最終日はアプリでは「推定」。公式の画面で確かめるよう常に添える。

## 1. 個人データの決まり(最優先)

リポジトリは public。次を必ず守る。

1. 購入計画、金額、購入記録、ウォッチ中の銘柄、通知ルールは、端末の `localStorage` だけに置く。リポジトリ、ビルド成果物(`site/data`)、Actions のログに出さない。
2. 通知に必要な情報(Push の購読情報とルール)は、ユーザーがアプリでコピーして GitHub Actions の Secret `PUSH_CONFIG` に貼る。コード側は Secret を読むだけで、内容を一切ログに出さない。件数も出さない(公開リポジトリのログは誰でも読めるので、通知の条件を満たした日が件数から分かってしまう)。出すのは成否だけ(6.3)。
3. VAPID の秘密鍵は Secret `VAPID_PRIVATE_KEY`。公開鍵は Actions の Variable `VAPID_PUBLIC_KEY` から `site/data/push.json` に書く(公開鍵は公開してよい)。鍵の生成と登録はユーザーが手元で `scripts/setup_push.py` を実行して行う。
4. コード、文書、テスト、既定値に、個人名、メールアドレス(GitHub の noreply と example ドメインを除く)、手元の絶対パス、実際の金額計画を書かない。計画の画面の既定値は空にする。
5. サイトは外部へ通信しない(CDN、Web フォント、解析タグを使わない)。CSP で `'self'` に限る。`robots.txt` で全拒否、`<meta name="robots" content="noindex,nofollow">` を付ける。
6. `scripts/privacy_check.py` が、追跡対象と未追跡(ignore されていない)ファイルを走査し、上の違反を見つけたら終了コード 1 にする。CI で毎回走らせる。

## 3. データ元(2026-11-22 に取得を確認済み)

| データ | 取得方法 | 備考 |
|---|---|---|
| 投信の基準価額 | 投資信託協会「投信総合検索ライブラリー」の CSV: `https://toushin-lib.fwg.ne.jp/FdsWeb/FDST030000/csv-file-download?isinCd=<ISIN>&associFundCd=<協会コード>` | 文字コードは cp932(応答ヘッダの utf-8 は誤り)。列は `年月日,基準価額(円),純資産総額（百万円）,分配金,決算期`。日付は `2026年11月20日` 形式。設定来の全期間 |
| 指数・ETF・VIX | yfinance(`Ticker.history(period="max", auto_adjust=False, actions=False)` の `Close`。未調整の終値) | `^NYFANG` は 2014-09-22 から。`^GSPC`、`ACWI`、`^VIX`。直近の終値の欠けは 3.3 |
| 為替 | yfinance `USDJPY=X` | |
| マクロ指標(金利、ドル指数) | yfinance の `Close`: `^TNX`、`^IRX`、`DX-Y.NYB` | 3.2、4.8。登録版 `ml-macro` と探索だけが使う |
| 祝日 | `holidays.country_holidays("JP")`、`holidays.financial_holidays("NYSE")` | |

取得は 3 回まで再試行(指数的に待つ)、タイムアウト 30 秒。HTTP の User-Agent は `nisa-buy-timing/0.1 (+https://github.com/Uni-K-Pip/nisa-buy-timing)`。基準価額の取得に失敗した銘柄は、代理系列(指数×為替)だけで計算を続け、`status.warnings` に記録する。指数の取得に失敗したら、その銘柄は基準価額だけで計算する。両方失敗したらビルドを失敗させる(前回の Pages が残る)。

為替は日足の始値と終値の両方を取得する(朝の為替に始値を使う。4.2)。

為替の誤った値を除く: 始値と終値のそれぞれについて、日次の対数変化 r が |r| ≥ 3% で、翌日の変化が逆向き、かつ 2 日の合計の絶対値が |r| の半分以下なら、その日の値を誤りとみなして除く(除いた日は直前の値を使う)。yfinance の `USDJPY=X` には 2008-04-08、2008-10-08、2008-12-08 にこの形の値があり、残すと円換算の系列に 1 日で 20% 前後の偽の上下ができる。最新の 1 点は翌日がないので判定しない。指数には使わない(実際の急落と急反発を消してしまう)。

### 3.2 マクロ指標の確認(2026-11-25)

Model B の結果を見る前に、系列そのものについて次を確かめた。比べた相手の FRED は確認にだけ使い、ビルドでは取得しない。

- 単位と定義: `^TNX` は米 10 年国債の利回り(%)。FRED の `DGS10` と 1990 年以降の同じ日付で比べて、絶対差の平均 0.011 ポイント、99% 点 0.049、相関 0.99998。`^IRX` は 13 週の財務省短期証券の割引率(%)で、債券換算の利回りではない。FRED の `DTB3`(割引率)との絶対差の平均は 0.013、`DGS3MO`(債券換算)とは 0.091。債券換算 `100 × 365d / (360 − 91d)`(d = 割引率 / 100)に直すと、`DGS3MO` との絶対差の平均は 0.023 になる。長短金利差(`^TNX` − 換算後の `^IRX`)と FRED の `T10Y3M` は、絶対差の平均 0.023、相関 0.9997(換算しないと平均で 0.08 ポイントずれる)。
- 0 以下の値: `^IRX` は 2020-03-19〜03-27 の 7 日が負(−0.03〜−0.11)。実際の値なので除かない。
- 飛び値: 1990 年以降で、0.3 ポイント以上動いて翌日に半分以上戻った日は、`^TNX` が 1 日、`^IRX` が 4 日(2000-12-13、2007-08-20、2008-09-24、2008-09-29)。2007 年と 2008 年は実際の急変。2000-12-13 は FRED より 0.46 低く、誤りの疑いがある。実際の急変を消さないため、除去はしない。ドル指数は、2% 以上動いて翌日に半分以上戻った日が 1 日(2008-10-10)。
- 休日: 1996-10 以降、株式市場が開いていて金利の値がない日が 15 日(債券市場の休日)。ドル指数は、株式市場の休場日にも値がある日が 57 日。最大の空きは 2001-09-10 の次が 09-17。系列ごとに日付がそろわないので、国内営業日の並びに直してから計算する(4.8)。
- 取得できる時刻: `^TNX` と `^IRX` の日足は 8:20〜15:00(米国東部時間)で、終値は日本時間の翌朝 5 時(夏は 4 時)に確定する。`DX-Y.NYB` は平日ほぼ 24 時間値が付き、日足の終値は 17 時の値とも 24 時の値とも一致しなかった(1 時間足と突き合わせた)。朝 7:30 に前日の日足が確定している保証がないので、1 日遅らせて使う(4.8)。2026-11-25 8:00 の取得では、3 系列とも 11-24 の値が出ていた。
- 入れなかったもの: FRED の日次系列は公表が 1 営業日遅れる(8:00 の時点で `DGS10` は 11-23 まで)。FRED の ICE BofA 信用スプレッドは直近 3 年分しか取れない。原油と金の先物(`CL=F`、`GC=F`)は 2000-08 から、`HYG` は 2007-04 から、`^VIX3M` は 2006-07 からで、S&P500 の検証期間が短くなる。月次の経済統計は改定と公表の遅れがあり、当時の公表値が要る。入れるときは、4.8 に特徴量の組を足して別の版にする。

### 3.3 直近の終値の欠け(2026-11-25 に確認)

Yahoo の日足は、直近の米国営業日の行があるのに、終値(`Close` と `Adj Close`)だけが null のことがある。null の行は使えないので、指数の最新の日付が 1 日古くなり、その銘柄は今日の推定点(4.2)がなくなる。

確認したこと(`ACWI` の 2026-11-24 の行。時刻は JST):

- 08:55 の取得では終値 148.14。11:01(Actions)の取得では最新の日付が 2026-11-23 になった。11:08 以降(手元)の取得で、2026-11-24 の行の終値が null で、始値、高値、安値、出来高は入っているのを確かめた。出来高は端数のある値(確定した日は 100 株単位)で、確定前の行だった。null になった時刻は確かめていない。
- 同じ時刻に、ETF と個別株(`SPY`、`QQQ`、`VT`、`IVV`、`URTH`、`ACWX`、`AAPL`)は同じく null、指数(`^GSPC`、`^NYFANG`、`^VIX`、`^TNX`、`^IRX`)は値があった。`period`、`start`、取得先のホストを変えても同じ。
- 同じ応答のメタ情報には、通常取引の最新値 `regularMarketPrice` = 148.14 と、その時刻 `regularMarketTime` = 2026-11-24 16:00:01(米国東部時間)が入っていた。08:55 に日足から得た値と同じ。
- 11:20 の取得ではまだ null で、11:30 の取得では終値 148.14(`regularMarketPrice` と同じ値)が入り、出来高も 100 株単位の値になっていた。欠けるのは、取引終了後に行が確定値へ置き換わるまでの一時的な時間帯(この日は 08:55 より後から 11:20 過ぎまで)。朝 7:30 の更新はその前だが、昼の実行(`main` への push、手動の実行、遅れた定時実行)は当たりうる。
- yfinance の `repair=True` は使わない。この行は埋まるが、過去の値も変える(`^IRX` の 2020-03 の負の値 7 日を 1/100 にする、`^VIX` に 13 行と `DX-Y.NYB` に 106 行を足す、`USDJPY=X` の 35 日を変える)。

補う条件。`DataSource.close` は、次をすべて満たすときだけ、最後の行の終値を同じ応答の `regularMarketPrice` で補う。

1. 最後の行の `Close` が欠けている。補うのは最後の行だけで、それより前の欠けは補わない。
2. その行の日付 D が NYSE の営業日(4.1 の暦。土日と休場日でない)。
3. メタ情報に、`regularMarketPrice`(有限の値)、`regularMarketTime`、`exchangeTimezoneName` がある。
4. `regularMarketTime` を取引所のタイムゾーン(夏時間を含む)に直した日付が D と同じ。別の日の値では補わない。
5. D の通常取引が終わっている。メタ情報の `currentTradingPeriod.regular` の終了時刻の日付が D なら、取得の時刻が終了時刻以降であること。D より後の日付なら終わっているとみなす。欄がないか、D より前なら補わない。
6. `regularMarketPrice` が、その行の安値以上、高値以下(同じ日の、同じ基準の値であることの確認。高値か安値が欠けるか 0 以下なら補わない)。

- 補う値は通常取引の値だけ。時間外取引の値(`preMarketPrice`、`postMarketPrice`)と、ほかの足(1 時間足、週足)の値は使わない。日足は時間外取引を含めずに取得する(yfinance の既定)。
- 計算に使うのは未調整の `Close` で、`Adj Close` は使わない。`regularMarketPrice` も未調整なので、基準は同じ。
- 条件を 1 つでも満たさなければ補わず、その行は欠けのまま落とす(最新の日付が 1 日古くなる)。ほかの銘柄と、基準価額だけで決まる値は計算を続ける。
- 補った値は、朝 7:30 の更新が日足から得る値と同じ性質の、確定前の終値。D の通常取引の終値より後の情報は入らない。毎回、全期間を取り直すので、Yahoo の行に終値が入れば、次の取得からはその値を使う。
- 補ったときも補えなかったときも、`meta.json` の `latest_close` に記録する(5 章)。補った実行の台帳の行には、補った系列を残す(4.9)。

直近日の欠けの検出。補えなかったときや、行そのものがないときのために、銘柄ごとに指数の最新の日付を確かめる。

- 期待する最新日: ビルドの時刻を `America/New_York` に直し、その日が NYSE の営業日で 16:00 以降ならその日、そうでなければ直前の NYSE の営業日。短縮取引の日も 16:00 で数える(遅い側に倒す)。
- 指数の最新の日付が期待する最新日より古ければ、`status.warnings` に「指数の直近の終値(期待する最新日)を取得できませんでした。(指数の最新の日付)までの値で計算しています。」を足し、`meta.json` の `latest_close.stale` に記録する。画面は `status.warnings` をそのまま出す。
- 米国が休場だった翌朝は、期待する最新日が休場の前の営業日になるので、警告は出ない(今日の推定点がないのは正常。4.9 の `no_estimate`)。暦にない臨時の休場は、取得の失敗と区別できないので警告が出る。
- 警告は表示と記録だけで、スコア、ML、検証の計算と、台帳の `missing` の理由は変えない(`no_estimate` のまま。指数の最新の日付は行の `inputs` に残る)。

## 4. 計算

### 4.1 営業日と受渡(`calendar.py`、`settlement.py`)

- 国内営業日: 平日で、日本の祝日でなく、12/31 と 1/1〜1/3 でない日。
- 注文できる日: 国内営業日で、銘柄の `order_closed_calendars`(NYSE の休場日)に当たらない日。
- 約定日: 注文日の `trade_lag_bd` 国内営業日後。
- 受渡日: 注文日を 1 日目として数えた `settle_bd_from_order` 番目の国内営業日。
- 年内受渡の最終注文日: その年の注文できる日のうち、受渡日がその年の最後の国内営業日以前になる最も遅い日。
- 確認用の値(テストに入れる): 2026 年、NYSE 休場(12/25)を考慮して、N=6 なら 2026-12-23、N=5 なら 2026-12-24、N=4 なら 2026-12-24(12/25 は注文不可)、NYSE を考慮しない N=4 なら 2026-12-25。2026 年の最後の国内営業日は 12/30。
- 同じ計算を PWA 側(`site/js/calendar.js`)にも持つ。両方に上の確認用の値のテストを書く。PWA は `site/data/calendar.json` の休日一覧を使う。

### 4.2 価格系列(`series.py`)

- 基準価額系列: CSV の基準価額。分配金がある日は再投資した値に調整する(調整係数 = 累積の (1 + 分配金 / 基準価額))。日付は日本の営業日。
- 代理系列: 指数終値 × USDJPY。国内営業日 t の代理値 `A[t]` は、t より前の最後の米国営業日の指数終値に、t の朝の為替を掛けた値。朝の為替は、日付 t の日足の始値(日本時間の朝 9 時ごろの値で、投信が使う当日 10 時の仲値に近い)。t の日足がまだなければ(朝の更新)、最新の終値(その時点の値)。米国が休場の日は指数を直前の値のままにし、為替だけ動かす。
  - 2026-11-25 に確認した残差(基準価額の日次騰落率 - `A` の日次騰落率)の標準偏差は、FANG+ と S&P500 が 0.22%、オルカンが 0.36%。為替を米国日付の終値で合わせると 1 日古い値になり、0.77〜0.80% に悪化する(v0.2 まではこの対応だった)。
  - 過去の再現では、朝 7:30 の更新より 1.5 時間ほど後の為替を使うことになる。そのぶん、推定の誤差は実運用よりわずかに小さく出うる。
- 推定基準価額(nowcast): 最新の基準価額の日付 D について、D より後の国内営業日 d の代理値 `A[d]` があれば(下の「最新の推定点」と同じ条件。対応する代理値は `A[D]`)、`最新基準価額 × 最新代理値 / 対応する代理値` を推定値にする。推定誤差の目安として、過去 1 年の「基準価額の日次騰落率 − 代理系列の対応する日次騰落率」の標準偏差(%)を添える。
- 確定系列 C(計算に使う主系列): 分配金を調整した基準価額。基準価額の開始日より前は、代理系列を国内営業日にそろえ(欠けた日は直前の値)、基準価額の初日で値が一致するように定数倍してつなぐ(延長)。基準価額がない銘柄は代理系列だけを使う。延長に使う指数は配当を含まないので、延長した期間の上昇率は実際の投信よりやや低い。2026-11-24 に確認した範囲は、S&P500 が 1996-10、オルカンが 2008-03、FANG+ が 2014-09 から。
- 推定系列 E(判断時点の値): 国内営業日 t について `E[t] = C[t-1] × A[t] / A[t-1]`。A は代理系列を国内営業日にそろえた値。t の朝(米国市場の終了後、当日の注文締切の前)までに得られる値だけで決まり、t の基準価額そのものは使わない。最新の推定基準価額と同じ式を過去の各日に当てはめたもの。延長した期間は C が代理系列そのものなので `E[t] = C[t]`(推定誤差なし)。
- 最新の推定点: 最新の確定値の日付 D より後の国内営業日 d に対応する代理値があれば、`E[d] = C[D] × A[d] / A[D]` を判断時点の最新値とする。なければ(夜の更新で当日の基準価額が出たあとなど)、最新値は確定値 `C[D]`。
- 確定値と推定値は混ぜない。C に推定値を入れない。画面とデータでは、推定を含む値に必ずその旨を付ける。

### 4.3 指標(`indicators.py`)

主系列 P(国内営業日ごと)から計算する。

| キー | 定義 | 画面の名前 |
|---|---|---|
| `dd252` | P / 直近 252 日の最高値 − 1 | 52 週高値からの下落率 |
| `ma200_dev` | P / 200 日移動平均 − 1 | 200 日移動平均からの乖離 |
| `ma25_dev` | P / 25 日移動平均 − 1 | 25 日移動平均からの乖離 |
| `rsi14` | Wilder の RSI(14) | RSI(14) |
| `fx_dev` | USDJPY / 200 日移動平均 − 1(`fx_component: true` の銘柄だけ) | 円安・円高の度合い |
| `ret5`、`ret20`、`ret60` | 騰落率 | |
| `vol20` | 日次対数収益率の 20 日標準偏差(年率) | |
| `vol_ratio` | vol20 / 252 日の同じ値 | |
| `vix`、`vix_chg20` | `^VIX` の終値と 20 日変化(取れたときだけ。日付は米国日付→翌国内営業日に対応) | |

判断時点の指標: 日 t の指標を、C の t-1 までの末尾に `E[t]` を足した系列で計算した値。確定の指標は C だけで計算した値。`fx_dev`、`vix`、`vix_chg20` は朝までに得られる値なので両者で同じ。`fx_dev` の為替は、朝の為替(4.2)を国内営業日で並べた系列を使い、200 日移動平均も国内営業日で数える。`E[t] = C[t]` なら両者は一致する。

### 4.4 買い時スコア(`score.py`)

- 各要素について、その時点までの直近 1260 日(約 5 年。足りなければ 120 日以上ある範囲)の中での百分位 `pct`(現在値以下の割合)を出す。未来のデータを使わない(t の値は t までのデータだけで決まる)。
- 安さ `cheapness = 100 × (1 − pct)`(値が低いほど安いとみなす要素: dd252、ma200_dev、ma25_dev、rsi14、fx_dev)。
- スコア = 重み付き平均。重みは dd252 0.30、ma200_dev 0.25、ma25_dev 0.15、rsi14 0.20、fx_dev 0.10。使えない要素は除いて重みを正規化する。
- 区分: 80 以上「かなり割安圏」、60〜79「割安寄り」、40〜59「中立」、20〜39「割高寄り」、20 未満「かなり割高圏」。いつも「過去 5 年の同じ投信との比較」と添える。
- 各要素に日本語の説明文を付ける。例: 「52週高値から −8.7%(過去5年で安い方から 12%)」。
- 確定スコア `S_C[t]` は確定の指標から、判断時点のスコア `S_E[t]` は判断時点の指標から出す。`S_E[t]` の百分位は、t の判断時点の値を、それより前の確定の値(直近 1259 日)と自分自身の中で順位づける。
- 画面の最新スコアは、最新の推定点があれば `S_E`(「推定基準価額を含む」と付け、確定値でのスコアと日付を併記)、なければ `S_C`。前回との差は、同じ種類の、前の国内営業日の値と比べる。
- 検証(4.6)は `S_E` を使う。朝に画面で見る値と同じ条件にするため。

### 4.5 機械学習(実験、`ml.py`)

- 目的変数: 約定日(t の翌営業日)の価格より、その 20 営業日後の価格のほうが安いか(`C[t+1+20] < C[t+1]`。価格は確定値。約定日は銘柄の `trade_lag_bd` で決まり、3 本とも翌営業日)。行は国内営業日ごと(注文できない日も含む)。画面の言い方は「20営業日待てば安く買えた確率」。
- 特徴量: 4.3 の dd252、ma200_dev、ma25_dev、rsi14、ret5、ret20、ret60、vol20、vol_ratio、fx_dev(対象なら)、vix と vix_chg20(取れたら)。学習には確定の指標を、予測には判断時点の指標(4.3)を使う。実運用で朝に得られる値と同じにするため。
- モデル: `StandardScaler` + `LogisticRegression(C=0.5, max_iter=1000)`。
- 特徴量の組: 上の特徴量を `base` と呼ぶ。4.8 の 5 つが `rates_dollar`。モデルは組の並びで決める。ML v1(登録の `id` は `ml`)は `base`、Model B(`ml-macro` v1)は `base` と `rates_dollar`。Model B の目的変数、モデル、ウォークフォワードの手順、買う日の決め方は ML v1 と同じ。
- Model B は、`rates_dollar` の系列がどれか取れないときは計算しない(特徴量を黙って減らさない)。特徴量が 1 つでも欠けた行は、学習にも予測にも使わない。
- ウォークフォワード検証: 750 件の学習データがたまってから、21 営業日ごとに学習し直し、次の 21 日を予測する。学習に使う行は、その時点で答えが確定している行だけ(行 i は i+1+20 が学習時点より前のときだけ。学習時点の朝には、その日の基準価額がまだ出ていない)。
- 指標: AUC、Brier、基準 Brier(その時点までの正例率で予測した場合)、Brier スキル = 1 − Brier / 基準 Brier、件数、10 分位の較正表。AUC と Brier スキルには 95% 区間を付ける。区間は、検証行を日付順に並べ、長さ 42 行(予測期間の 2 倍)の連続ブロックを復元抽出する円環ブロック・ブートストラップ(2,000 回、乱数の種は固定)の 2.5% 点と 97.5% 点。予測期間が重なる行どうしの相関を区間に反映するため。重ならない予測期間の数(件数 ÷ 21 の切り捨て)も出す。
- 有効の判定: 次をすべて満たすとき `valid: true`。件数 250 以上、AUC 0.55 超、Brier スキル 0.01 超(ここまでが性能の基準)、AUC の 95% 区間の下限 0.5 超、Brier スキルの 95% 区間の下限 0 超(偶然でないことの基準)。満たさなければ `valid: false` とし、画面に「過去の検証では偶然と区別できません。参考にしないでください」と大きく出す。
- `valid` は予測指標の基準であり、購入判定に使ってよいかは 4.7 で決める。
- 基準日(4.7)より後に予測した行だけの件数、AUC、Brier スキルと区間を `forward` として出す(未使用データでの途中経過)。
- 推定誤差の影響: 基準価額のある期間について、判断時点の指標で予測した確率と、確定の指標で予測した確率の差(絶対値の平均と 95% 点)、および確定の指標で予測した場合の AUC と Brier スキルを出す。
- 最新の確率は、答えが確定している全行で学習したモデルに、最新の判断時点の指標を入れて出す。前回の確率は、その前の国内営業日について同じ手順で出す。
- モデルを比べるとき(マクロ指標を足した版など)は、有効・無効だけで比べない。同じ検証行を対にしたブロック・ブートストラップで、既存モデルとの差(AUC、Brier スキル、4.6 の主条件の差)とその 95% 区間を出す。比べ方は 4.10。

### 4.6 検証(`backtest.py`)

「決めた日に分けて買う」と比べて、スコアを見て買うと平均取得単価がどう変わったかを過去データで調べる。

- 時間の並び: 銘柄の注文できる日(4.1)を古い順に並べた列で数える。判断は注文できる日 t の朝に `S_E[t]` で行い、その日の締切までに注文し、約定は t の `trade_lag_bd` 国内営業日後の確定値。注文できない日のシグナルは使わない。朝の更新(7:30)より前に締切がある銘柄は、注文を次の注文できる日に送る。
- 期間 W 日(注文できる日で数える)、回数 K、各回同額。k 回目の小区間は `[floor(k·W/K), floor((k+1)·W/K) − 1]`。
- 定期購入(基準): 各小区間の初日に買う。
- 一括: 期間の初日に全額。
- スコア戦略(閾値 T): 各小区間で、スコアが T 以上の最初の日に買う。なければ小区間の最終日に買う。すでに今の回を買ったあと、スコアが T+15(上限 95)以上なら次の回を前倒しで買ってよい(1 日 1 回まで)。
- ML 戦略(q = 0.4): 各小区間で「待てば安く買えた確率」が q 以下の最初の日に買う。なければ最終日。ウォークフォワードの予測がある期間だけ。
- 平均取得単価は同額購入なので調和平均。比較値 = 戦略の平均単価 / 定期購入の平均単価 − 1(%、負なら安く買えた)。
- 開始日は 5 営業日ごと。グリッド: W ∈ {20, 40, 60, 120}、K ∈ {1, 2, 3, 4, 6}(K ≤ W)、T ∈ {60, 70, 80}。
- 偽シグナル(待ち方だけをまねた比較相手): 同じ銘柄・同じ条件で、開始位置が W 以上離れたほかのすべての期間について、実際の戦略がその期間で選んだ買う日の位置を、いまの期間の価格に当てはめて平均取得単価を出し、その平均をとる。待つ日数の分布は実際の戦略と同じで、価格とは無関係になる。これより安ければ、遅く買う不利を除いたうえでシグナルに情報がある。
- 比べる相手は 3 つ。対定期 = 戦略の単価 / 定期購入の単価 - 1。対一括 = 戦略の単価 / 一括の単価 - 1。対偽シグナル = 対定期の差 - 偽シグナルの対定期の差(ポイント)。どれも負なら安い。定期購入より平均で何日遅く買ったか(買う日の位置の平均の差)も出す。
- 対象期間は、期間の初日で分ける。`all` = 延長を含む全期間、`nav` = 基準価額の開始日以降、`recent_3y` = 最新日の 3 年前以降。判定用に、`history` = 最後の約定日が基準日(4.7)以前(探索に使った過去データ)、`forward` = 初日が基準日より後(条件を固定したあとの未使用データ)。基準日をまたぐ期間はどちらにも入れない。
- 出す値: 件数、重ならない期間の数、平均、中央値、勝率(安く買えた割合)、5% 点と 95% 点、平均の 95% 区間。
- 区間: 期間を開始日の順に並べ、長さ `ceil(2W/5)` 個(2W 日ぶん)の連続ブロックを復元抽出する円環ブロック・ブートストラップ(2,000 回)の 2.5% 点と 97.5% 点。開始日が近い期間は同じ日を共有するので、独立とみなさない。乱数の種は銘柄、条件、比較、対象期間から決め、同じデータなら同じ結果にする。期間の数がブロック長の 2 倍に満たなければ区間は出さない。
- 推定誤差の影響: 基準価額のある期間について、`S_E` と `S_C` の差(絶対値の平均と 95% 点)、区分が食い違う日の割合、閾値 70 の判定が食い違う日の割合、主条件で `S_C` を使った場合と `S_E` を使った場合の対定期の差を出す。

### 4.7 有効性の判定(`validation.py`、`config/validation.json`)

買い方や予測モデルを購入判定に使ってよいかを、結果を見る前に決めた手順で判定する。基準は、偶然でないこと(統計)だけでなく、実際に安く買えること(買い方としての成績と改善幅)で置く。この節の数値は 2026-11-25 に、2026-11-24 より後のデータを見ずに決めた。最初の版(スコア v1、ML v1)の基準日は 2026-11-25。

Model B(`ml-macro` v1。4.5、4.8)も 2026-11-25 に登録した。登録の前に見たのは、マクロ指標の系列そのもの(履歴の長さ、単位、欠損、取得できる時刻。3.2)だけで、Model B の予測と検証の結果は見ていない。

- 判定の単位: 買い方の版 × 銘柄 × 比較相手(対定期、対一括、対偽シグナル)。3 銘柄は値動きが連動するので、3 本で同じ結果が出ても独立した 3 回の確認とはみなさない。
- 主条件: 期間 40 日、3 回。スコア戦略は閾値 70、ML 戦略は確率 0.4 以下。判定は主条件だけで行う。グリッドのほかの条件は参考で、判定に使わない。グリッドのうち 95% 区間がゼロをまたがない条件の数を並べて出す(偶然でも 5% 前後は出る)。
- 実用的な改善幅 δ: 平均取得単価で 0.5%。平均の改善がこれに届かない買い方は、区間がゼロをまたがなくても採らない。
- 状態は 4 つ。
  - 有効性未確認(`unconfirmed`): 下のどれにも当たらない。区間がゼロをまたぐ場合を「効果がない」とは書かない。
  - 過去は不利(`unfavorable`): `history` の差の 95% 区間の下限が 0 を超える。
  - 候補(`candidate`): `history` で、平均が -δ 以下、95% 区間の上限が 0 未満、重ならない期間だけで作った t 分布の 95% 区間の上限も 0 未満、かつ基準価額のある期間に限った平均も負。
  - 確認済み(`confirmed`): 候補であり、直近の判定日の時点の `forward` で次をすべて満たす。基準日から 2 年以上、重ならない期間が 12 個以上(これは下限で、満たしただけでは足りない)。平均が -δ 以下。補正後の水準の区間(ブロック・ブートストラップ、50,000 回)の上限が 0 未満。同じ水準の、重ならない期間だけの t 区間の上限も 0 未満。
- 判定日: 基準日の 2、3、4、5、6 年後の同じ月日の 5 回だけ。判定には、最後の約定日が判定日以前の `forward` の期間だけを使う。判定日と判定日のあいだは状態を変えない。6 年後の判定でも確認済みにならなければ、その版の前向き検証を終える(候補だった比較は有効性未確認に戻す。過去は不利は `history` についての事実なので残す)。
- 補正: 繰り返し判定することと、複数の版を試すことによる偽陽性を抑えるため、判定の区間の水準を `1 - 0.05 / (判定回数 5 × 同時に前向き検証にかける版の上限 5)` = 99.8% に固定する(ボンフェローニ)。あとから版を足しても、先に始めた版の基準は変えない。同時にかける版は 5 つまで。
- 途中経過: 確認済みになる前も、`forward` の件数、重ならない期間の数、平均、95% 区間、基準日からの経過、次の判定日を常に出す。途中経過の区間は判定に使わない。
- 採用の条件:
  - 対一括が確認済み → 一括より有利な買い方として使える。
  - 対定期と対偽シグナルがともに確認済み → 分けて買うときの日の選び方として使える。この場合も、対一括の結果を必ず並べて出す。
  - 予測モデルは、4.5 の `valid` を満たしても、そのモデルを使う買い方が上の条件を満たすまで購入判定に使わない。
  - 市場環境の指標などを足すときも、重みと閾値を版として登録し、同じ手順で確認済みになってから購入判定に使う。確認済みになるまでは、判定と切り離した情報として出す。
- 版の管理(`config/validation.json`、`schema` は 2): `strategies` に、前向き検証にかける版を並べる(同時に 5 つまで)。版ごとに `id`(一意。出力のキーになる)、`kind`(`score` か `ml`)、`version`、`registered`(基準日)、`primary`(主条件)、`fingerprint` を持つ。`kind` が `ml` の版は `features`(特徴量の組の並び。先頭は `base`)も持つ。版が固定するのは、指標と重みと百分位の窓(スコア)、買う日の決め方、特徴量と目的変数とモデルと学習の手順(ML)、主条件。どれかを変えるときは `version` を上げ、`registered` をその日に改める。`forward` は新しい基準日から数え直す。旧版は `retired` に、基準日、終了日、銘柄ごとの最終の結果(件数、平均、区間、状態)を残す。
- いまの版: `score` v1、`ml` v1(`base`)、`ml-macro` v1(`base`、`rates_dollar`)。基準日はどれも 2026-11-25。
- `fingerprint` は、固定の合成データに対する出力(スコアの系列、主条件で買う日の並び、ML の特徴量名・目的変数・モデルの設定・学習に使う行)から作る SHA-256 の先頭 16 桁。`base` 以外の組を含む ML の版は、組の並びと、合成のマクロ系列から作ったその組の特徴量の値も入れる。登録された値と一致することをテストで確かめる。食い違えば、判定ロジックを変えたのに版を上げていない。
- 新しい予測対象、モデル、閾値を判定にかけるときは、結果を見る前に版として登録する。登録せずに試した結果は探索として扱い、状態を付けない。
- 登録版と探索を分ける: 登録版は `config/validation.json` にある版だけ。毎日のビルドが、登録版の `evidence`(`backtest/<id>.json`)と `registered/<id>.json` を出し、台帳(4.9)に当時の予測を残す。探索(4.10)は `--explore` を付けた手元のビルドだけが計算し、状態を付けず、`site/data` にも台帳にも書かない。
- 計算できない版(Model B でマクロ指標が取れないとき)は、その実行では `evidence` を出さず、理由を記録する。ほかの版の出力は変えない。

### 4.8 マクロ指標(`macro.py`)

登録版 `ml-macro` と探索(4.10)が使う。画面とスコアには使わない。

- 系列(3.2 で確認): `us10y` = `^TNX`(%)、`us3m` = `^IRX`(割引率 %。債券換算 `100 × 365d / (360 − 91d)`、d = 値 / 100 に直してから使う)、`dxy` = `DX-Y.NYB`。金利は 0 以下の値も除かない。
- 朝の値: 米国日付 D の値は、D に「遅れ」の日数を足した暦日より後の、最初の国内営業日の朝から使える。遅れは `us10y` と `us3m` が 0(VIX と同じ扱い)、`dxy` が 1。同じ国内営業日に複数の値が当たるときは、新しいほうを使う。新しい値が来ない日は直前の値を使うが、5 国内営業日を超えて続いたら欠けとする(古い値を使い続けない)。こうして国内営業日ごとに並べた系列から特徴量を作る。
- 特徴量の組 `rates_dollar`(国内営業日で数える):

| キー | 定義 |
|---|---|
| `us10y_chg20` | `us10y[t] − us10y[t−20]`(ポイント) |
| `term_spread` | `us10y[t] − us3m[t]`(ポイント。10 年 − 3 か月) |
| `term_spread_chg20` | `term_spread[t] − term_spread[t−20]` |
| `dxy_dev` | `dxy[t]` / `dxy` の直近 200 日の平均 − 1 |
| `dxy_ret20` | `dxy[t] / dxy[t−20] − 1` |

- 計算に使う値が 1 つでも欠けた日は、その特徴量を欠けとする。金利の水準そのものは年代で大きく変わるので、特徴量にしない。
- 朝までに得られる値だけで決まるので、確定の指標と判断時点の指標で同じ値になる(4.3 の `vix` と同じ)。
- 取得できなかったとき: 3 系列のどれかが空なら `rates_dollar` は使えない(理由 `macro_unavailable`)。既存の出力(スコア、ML v1、検証、通知)は変えずに続ける。画面の警告(`status.warnings`)には足さない。
- 組を足すとき(原油、金、信用スプレッド、経済統計、ニュースなど): 系列の定義(ティッカー、遅れ、変換)と特徴量の組を足し、版の `features` に組の名前を並べる。既存の組の定義は変えない(変えるなら、その組を使う版を上げる)。

### 4.9 台帳(`ledger.py`)

登録版の前向き検証について、その日の朝に出した予測を、あとから書き換えない形で残す。判定(4.7)は再計算した系列で行い、台帳はその照合に使う(台帳には、基準日から記録を始めるまでの日と、実行に失敗した日がないため)。台帳に入るのは、公開の価格と指標から計算した値だけで、購入計画、金額、通知の条件は入らない。

- 置き場所: ビルドの `--ledger <フォルダ>`。指定がなければ読み書きしない(手元のビルドと探索は台帳に触れない)。Actions はブランチ `forward-log` を取り出して渡し、足した行を別のジョブがそのブランチへ commit する(7 章)。ブランチの履歴が、その行がいつ足されたかの記録になる。ファイルは `<版の id>/v<version>/<銘柄 id>.jsonl`(1 行 1 記録の JSON、UTF-8)。
- 書くとき: JST の今日が国内営業日で、実行の時刻がその銘柄の注文締切より前のビルド。登録版 × 銘柄ごとに 1 行。
- 行の内容: `date`(判断の対象日 = 今日)、`recorded_at`(予測の日時)、`run_kind`、`strategy`、`version`、`fingerprint`、`commit`(環境変数 `GITHUB_SHA`。なければ null)、`fund`、`status`(`ok` か `missing`)、`reason`、`basis`、`orderable`(注文できる日か)、`signal`(スコアまたは確率)、`condition`(主条件の閾値)、`condition_met`(仮想の購入判定 = その日に買う条件を満たしたか)、`features`(予測に使った判断時点の特徴量)、`inputs`(基準価額、指数、為替、VIX、マクロ指標の最新の日付。その実行で終値を補った系列(3.3)が指数、VIX、マクロ指標の中にあるときだけ、`filled` にそのティッカーの一覧を足す)、`train`(学習に使った行数と最後の行の日付。ML だけ)。数値は小数 6 桁に丸める。
- 仮想の購入判定は、その日の値が主条件の閾値を満たしたかだけを記録する(スコア ≥ 70、確率 ≤ 0.4)。小区間の最終日に買う扱いと前倒しは、期間の区切りで決まるので行には入れない。
- ML の `signal` は、検証と同じ学習時点のモデルで出す: 今日の行の位置以前で最後の学習時点(4.5 の 21 営業日ごとの並び)で学習したモデルに、今日の判断時点の特徴量を入れる。画面の確率(最新まで学習。4.5)とはわずかに違いうる。
- `missing` の理由: `no_estimate`(今日の推定点がない。米国が休場だった翌朝など)、`macro_unavailable`(4.8)、`features_incomplete`(特徴量に欠け。古い値の打ち切りを含む)、`model_unavailable`(学習行が足りないなど)。
- 書き換えない: 行は末尾に足すだけで、既存の行を変えず、消さない。同じ日付の `ok` の行がすでにあれば足さない。`missing` の行は、同じ日付に `ok` の行も同じ理由の `missing` の行もないときだけ足す(朝のうちにやり直して成功したら `ok` の行が足される)。読むときは、日付ごとに最初の `ok` の行を使い、なければ `missing` とする。
- 照合: `--ledger` があるビルドは、登録版 × 銘柄ごとに、台帳の最初と最後の日付、`ok` の日数、理由ごとの `missing` の日数、行がない国内営業日の数、再計算した値(スコアは `S_E`、ML はウォークフォワードの確率)と比べられた日数、絶対差の平均と最大、買う条件が食い違った日数を出す。朝の為替は実運用と再計算で時刻が違う(4.2)ので、小さな差は出る。
- 失敗の扱い: 台帳の読み書きに失敗しても、ほかの出力は変えずに続け、`meta.json` に失敗を記録する。

### 4.10 探索(`explore.py`、`--explore`)

登録していない予測対象とモデルを、過去データで比べる。探索の結果には状態(4.7)を付けず、購入判定に使わない。良い結果が出ても、版として登録し、4.7 の手順で確認済みになるまでは使わない。この節の対象、モデル、買う条件は 2026-11-25 に、結果を見る前に決めた。結果を見てから閾値や条件を変えない(変えるなら、変えたことと理由を記録に残し、試した数に数える)。

- 実行: `python -m nbt.build --out site/data --explore <出力フォルダ>`。毎日の Actions では実行しない。`site/data` と台帳には何も足さない。出力は `<出力フォルダ>/<銘柄 id>.json` と `<出力フォルダ>/report.md`。マクロ指標が取れなければ、通常の出力を書いたあとで失敗させる。
- モデル: A = `base`、B = `base` と `rates_dollar`。A と B は同じ行で比べる: 学習に使える行は B の確定の特徴量がすべてそろった行、予測する行は B の判断時点の特徴量がすべてそろった行とし、A もその行だけを使う。学習の時点、学習に使う行、予測する行、基準(下記)は A と B で同じになる。
- 予測対象(3 銘柄共通。`P0` = 約定日の価格 `C[t+lag]`、h = 予測期間の営業日数):

| キー | 種類 | 定義 | h |
|---|---|---|---|
| `down20` | 二値 | `C[t+lag+20] < P0`(既存の目的変数。A と B の主比較) | 20 |
| `ret5`、`ret10`、`ret20` | 連続 | `C[t+lag+h] / P0 − 1` | 5、10、20 |
| `drop3_10`、`drop5_10`、`drop3_20`、`drop5_20` | 二値 | `min(C[t+lag+1 .. t+lag+h]) / P0 − 1 ≤ −x`(x = 3%、5%) | 10、20 |
| `low20` | 連続 | `min(C[t+lag+1 .. t+lag+20]) / P0 − 1`(約定価格から期間内の最安値まで。正なら一度も下回らなかった) | 20 |
| `vol20` | 連続 | `C[t+lag .. t+lag+20]` の日次対数収益率 20 個の標準偏差 × √252 の自然対数 | 20 |

- 答えなしの行: `down20` と `ret*` は両端の価格(`P0` と `C[t+lag+h]`)のどちらかが欠けた行(`down20` は 4.5 の目的変数と同じ)。期間内の価格を使う `drop*`、`low20`、`vol20` は、`C[t+lag .. t+lag+h]` のどれか 1 つでも欠けた行。`vol20` で標準偏差が 0 の行も答えなし。
- 学習と予測: 4.5 と同じウォークフォワード(750 件、21 営業日ごと)。学習に使う行は、答えが学習時点より前の価格だけで決まる行(行 i は `i + lag + h` が学習時点より前)。学習には確定の指標、予測には判断時点の指標を使う。二値は 4.5 と同じモデル。連続は `StandardScaler` + `Ridge(alpha=1.0)`(scikit-learn の既定値。調整しない)。
- 基準: その学習時点で学習に使った行だけから出す、目的変数の平均(二値なら正例率)。予測と同じ時点までのデータだけで決まる。
- 予測の評価(買い方の評価とは別に出す): 対象 × モデルごとに、全検証行(`all`)と基準価額のある期間(`nav`)で出す。
  - 二値: 件数、正例数、負例数、正例率、AUC、Brier、基準 Brier、Brier スキル、AUC と Brier スキルの 95% 区間(4.5 と同じ方法)。
  - 連続: 件数、目的変数の平均と標準偏差、スキル(1 − 二乗誤差の和 / 基準の二乗誤差の和)、順位相関(予測と実際の値に全検証行で順位を付け、その順位どうしの相関係数)、それぞれの 95% 区間。
  - 区間のブロック長は `2 × (lag + h)` 行。
  - B と A の差(B − A): 二値は AUC と Brier スキル、連続はスキルと順位相関。同じ検証行を対にしたブロック・ブートストラップ(抽出した同じ行で A と B の両方を計算し、差の 2.5% 点と 97.5% 点)で 95% 区間を出す。
- 買い方の評価(主条件の期間 40 日・3 回。数え方は 4.6):
  - 登録の買い方: `down20` の確率が 0.4 以下の最初の日に買う(ML v1 と ml-macro v1 の主条件)。A と B の主比較はこれで行う。
  - 探索の共通ルール: 予測が基準より「待つと不利」の側にある最初の日に買う。基準と等しいときは買う。

| 対象 | 買う条件 |
|---|---|
| `down20`、`drop3_10`、`drop5_10`、`drop3_20`、`drop5_20` | 予測確率 ≤ 基準(正例率) |
| `ret5`、`ret10`、`ret20` | 予測 ≥ 基準(平均) |
| `low20` | 予測 ≥ 基準(平均。下落が平時より浅い) |
| `vol20` | 買い方に変換しない(値動きの大きさで、方向がない) |

  - 条件を満たさないまま小区間の最終日になったら、その日に買う(4.6 のスコア戦略、ML 戦略と同じ)。前倒しはしない。
  - 比較の条件をそろえる: `vol20` を除くすべての対象 × モデルの予測がそろった日だけを使い、どの買い方も同じ期間の集合で比べる。定期購入、一括、偽シグナルの出し方は 4.6 と同じ。
  - 出す値: 買い方ごと、対象期間(`all`、`nav`)ごとに、件数、重ならない期間の数、対定期・対一括・対偽シグナルの平均、中央値、勝率、5% 点と 95% 点、95% 区間、遅れた日数。
  - 既存モデルとの差: 「A の登録の買い方」(ML v1 と同じ条件)を基準に、各買い方の対定期・対一括・対偽シグナルを期間ごとに対にして引き、平均と 95% 区間(4.6 と同じブロック長)を出す。
  - B と A の差: 同じ対象・同じルールの買い方どうしで、同じく対にして出す。
- A と ML v1 の照合: 探索の A(`down20`)の予測と、毎日のビルドの ML v1 の予測について、行数と、確率の絶対差の最大を出す。マクロ指標で除かれる行がなければ一致する。
- 試した数(多重比較): 対象の数、モデルの数、予測の評価の組の数、買い方の数、比較の数(出そうとした区間の数)と、95% 区間が基準をまたがない数を、予測の指標(AUC は 0.5、ほかは 0 が基準)、予測指標の B − A、買い方、A の登録の買い方との差、買い方の B − A に分けて出す。A の登録の買い方そのものには、それとの差を出さない。区間は補正していないので、差がなくても 5% 前後はゼロをまたがない。対象どうし、銘柄どうしは連動するので、独立した確認の数ではない。
- 再現に要る情報: 実行の時刻、Git のコミットと未コミットの変更の有無、Python と主なライブラリの版、価格とマクロ指標の最初と最後の日付、行数(全体、特徴量がそろった行、マクロ指標で除いた行)、設定(学習の件数と間隔、抽出回数、ブロック長、乱数の種の決め方)、登録版の fingerprint。手元の絶対パスは入れない。
- 記録: 結果は良否にかかわらず、`report.md` を `docs/experiments/<日付>-<名前>.md` に置いて残す。区間がゼロをまたぐ結果は「有効性未確認」と書き、「効果がない」と書かない。
- 読み方の限界: Model B の結果は、この 5 つの特徴量とこのモデルについての結果であり、ほかのマクロ指標(原油、金、信用スプレッド、経済統計)やニュースの有効性を示さない。共通ルールは探索用で、最もよい条件だと確かめたものではない。

## 5. ビルドの出力(`python -m nbt.build --out site/data`)

すべて UTF-8 の JSON。数値は丸める(価格は小数 2 桁、% は小数 2 桁)。個人データは入れない。

- `latest.json`: `schema`、`generated_at`(JST の ISO 8601)、`run_kind`、`disclaimer`、`sources`(名前と URL)、`funds[]`。各 fund に `id`、`name`、`short_name`、`series_kind`(`nav`/`proxy`)、`nav`(日付、値、前日比)、`nowcast`(基にした米国日付、推定値、変化率、誤差の目安)、`proxy`(指数のティッカー・名前・日付・値・前日比、為替の値)、`score`(値、区分、区分名、要素の一覧と説明、基準日)、`ml`(確率、基準日、`valid`、指標、注記)、`settlement`(`verified`、各パラメータ、今年の年内受渡の最終注文日と受渡日と残り営業日、今後 5 回の注文できる日)、`status`(取得の成否と警告)。
- `latest.json` の `score` と `ml` は `basis` を持つ(`estimate` = 推定基準価額を含む、`confirmed` = 確定値だけ)。`estimate` のとき、`score.confirmed` に確定値でのスコア(値、区分、区分名、基準日)を入れる。`score.date` と `ml.date` は、その値が対応する国内営業日。
- `series/<id>.json`: `dates`、`value`(確定系列。基準価額の開始日以降だけで、延長した部分は載せない)、`nav`、`proxy_jp`(円換算の代理値)、`index`、`score`(確定スコア)、`ml_prob`。欠けは null。推定点は載せない。
- `backtest/<id>.json`: 4.6 のグリッドの結果と、条件の説明文。各戦略・各対象期間(`all`、`nav`、`recent_3y`)の値は、従来の位置(`count`、`mean`、`median`、`win_rate`、`p05`、`p95` = 対定期)に残し、`ci`(`[下限, 上限]` または null)、`independent`、`delay`、`vs_lump`、`vs_placebo`(それぞれ `mean`、`median`、`win_rate`、`p05`、`p95`、`ci`)を足す。一括には `vs_lump` と `vs_placebo` を付けない。ほかに `periods`(各対象期間の最初と最後の日付)、`evidence`(4.7。版、基準日、主条件、判定日の一覧、次の判定日、水準、比較相手ごとの `status` と `history`・`history_nav`・`forward`・`judgment` の値)、`grid_summary`(戦略と比較相手ごとに、`all` の区間がゼロより下の条件の数、上の条件の数、区間を出せた条件の数)、`estimate_impact`。
- `ml/<id>.json`: 4.5 の指標と較正表、`auc_ci`、`brier_skill_ci`、`independent`、`forward`、`estimate_impact`。ML v1 の値で、形は変えない。
- `backtest/<id>.json` の `evidence.strategies` は、登録版の `id` ごと(`score`、`ml`、`ml-macro`)。計算できなかった版は `comparisons` を null にし、`unavailable` に理由を入れる。グリッドと `grid_summary` は従来どおり `score` と `ml` だけ。
- `registered/<id>.json`(登録版の前向き検証。画面では使わない): `schema`、`strategies`(登録版の `id` ごと)。各版に `kind`、`version`、`registered`、`fingerprint`、`available`、`reason`、`decision`(今日が判断の日なら、台帳に書く行から `features`、`inputs`、`train` を除いたもの。そうでなければ null)、`ledger`(4.9 の照合。`--ledger` がなければ null)。`ml` 以外の ML の版には、`features`(組の並び)、`feature_names`、`metrics`(`ml/<id>.json` と同じ形)、`coverage`(国内営業日の数、`base` がそろった行、すべてそろった行、マクロ指標で除いた行、予測した行、最初の予測日)、`macro`(系列ごとのティッカー、遅れ、最新の日付)も入れる。
- `meta.json` に、`macro`(系列ごとの最新の日付と、使えるか)と、`--ledger` があるときの `ledger`(足した行数と成否)を足す。
- `meta.json` の `latest_close`(3.3): `expected_us_date`(期待する最新日)、`filled`(終値を補ったティッカーごとに、`date`、`close`(補った値。小数 4 桁)、`source`(`regularMarketPrice`)、`price_time`(その値の時刻。取引所の時刻)、`fetched_at`(取得の時刻。JST))、`unfilled`(最後の行の終値が欠けていて補えなかったティッカーごとに、`date`、`reason`、`fetched_at`。理由は `not_trading_day`、`no_price`、`date_mismatch`、`session_open`、`session_unknown`、`out_of_range`)、`stale`(最新の日付が期待する最新日より古い指数のティッカーごとに、その最新の日付)。該当がなければ空のまま出す。
- `--explore <フォルダ>` を付けたときだけ、4.10 の `<フォルダ>/<id>.json` と `<フォルダ>/report.md` を書く。`--out` の下には書かない。
- `calendar.json`: 今年と来年の、日本の休業日(祝日と年末年始)と NYSE の休場日。
- `push.json`: `{"vapid_public_key": "<環境変数 VAPID_PUBLIC_KEY の値>" | null}`。
- `meta.json`: ビルドの時刻、各データの最新日付、取得の成否。

取得部分は差し替えられるようにし、テストではネットワークを使わずに偽のデータでビルドを通す。

## 6. PWA(`site/`)

- ビルド不要の静的ファイル。ES modules。外部ライブラリを使わない(チャートは自前の SVG)。相対パスだけを使う(Pages では `/nisa-buy-timing/` の下に置かれる)。
- スマホ向けの縦画面(幅 320〜430px)を主に、PC 幅でも使える日本語の画面。ライトとダークに対応し、下部の SVG アイコン付きタブで画面を切り替える。区分や値動きには色と文字・記号を使い、操作にはキーボードでもフォーカスできる。
- `sw.js`: アプリの殻をキャッシュ(オフラインで開ける。入れるときはブラウザの HTTP キャッシュを通さずに取り直す)。`data/` はネットワーク優先、失敗したらキャッシュ。`push` を受けて通知を出し、通知を押したらアプリを開く。版を上げたら古いキャッシュを消す。
- `manifest.webmanifest`、アイコン(192、512、apple-touch-icon 180 の PNG)。iOS でホーム画面に追加できるメタタグ。
- CSP は meta タグで `default-src 'self'; img-src 'self' data:; style-src 'self'; script-src 'self'; connect-src 'self'; manifest-src 'self'; worker-src 'self'; base-uri 'none'; form-action 'none'; object-src 'none'`。インラインのスクリプトとスタイルを使わない。
- 初回起動時に注意書き(投資助言ではない、予測は外れうる、締切や受渡日は公式で確認、SBI 証券とは無関係)を出し、同意を `localStorage` に残す。どの画面の下部にも短い注意書き。

### 6.1 画面

1. **今日**: 閉じられる初回案内に、スコアの読み方と区分の凡例、計画と通知への案内を表示する。ウォッチ中の銘柄ごとに、5 区分の半円メーターと整数スコア(切り捨て。区分の下限と食い違わせない)、前回との差、全要素の内訳を表示する。基準価額、推定基準価額、指数、為替は、値動きと日付を添えた価格タイル。データの日付と更新の警告、年内受渡の最終注文日(推定)と残り国内営業日、注文可能日の表と用語の説明を表示する。計画があれば次の回、各回の状態、公式の最終注文日、確認結果を表示する。ML の確率は実験と明示し、無効の警告は常に表示する。スコアと ML の確率が推定基準価額を含むときは、その旨と対応する日付を添え、確定値でのスコアと基準日を併記する。
2. **チャート**: 銘柄と期間(1 年、3 年、全期間)を区切り付きのボタンで選ぶ。表示幅に合わせて価格とスコアの折れ線、目盛り、区分の色、端末の購入記録の破線を描く。図を指やマウスでなぞるか、左右キーで移動すると日付、価格、スコアと区分が読める。
3. **計画**: 計画の一覧に注文・約定の進み具合、予算に対する注文済み金額、各回の状態、確認結果の件数を表示する。編集は基本、買う日と金額、買う目安、年内の枠の確認に分ける。折りたたみを開いた状態は再描画をまたいで保持する(6.2)。
4. **検証**: 計画の条件(期間 = 計画の最初の予定日から最後の予定日までの営業日数に近い W、回数 K、閾値 T)に最も近いグリッドの結果を表示する。計画がなければ既定値(W=40、K=3、T=70)。結論の文を表示し、定期購入を基準として各戦略の平均・中央値・5% 点〜95% 点、安く買えた割合を図で比較する。図は対象期間(全期間 = 過去へ延長した分を含む、基準価額のある期間、直近 3 年)を切り替えられ、詳しい表と検証方法は折りたたみで確認できる。買い方ごとに、対定期・対一括・対偽シグナルの平均と 95% 区間、定期購入より遅れた日数を出す。主条件を表示しているときは、4.7 の状態(有効性未確認、過去は不利、候補、確認済み)を比較相手ごとに出す。主条件でないときは「参考(判定には使いません)」と出す。区間がゼロをまたぐ結果を「効果がない」と書かず、「有効性未確認」と書く。前向き検証の途中経過(版、基準日、件数、重ならない期間の数、平均、区間、次の判定日)を、探索に使った過去データの結果と分けて出す。推定誤差の影響と、グリッドのうち区間がゼロをまたがない条件の数も出す。ML は有効・無効を明示し、予測確率と実際の割合の較正図と指標・較正表、AUC と Brier スキルの 95% 区間、基準日より後の値を表示する。
5. **設定**: ウォッチする銘柄の選択、通知の 3 手順(購読、条件の選択、コピーと GitHub への登録)、データの置き場所、端末データの書き出し・読み込み・全削除、注意書きと初回案内の再表示、データ元の一覧。

### 6.2 購入計画(`site/js/plan.js` は DOM に触れない純粋な関数で書き、node:test で試す)

計画のデータ:

```
{ id, fund_id, title, year, budget, threshold_score (既定 70), pull_forward_score (既定 85),
  levels: [{kind: "index"|"nav", op: "<=", value}],
  drop_rule: {kind: "index"|"nav", reference_value, pct} | null,
  installments: [{id, planned_date, amount, status: "planned"|"ordered"|"executed"|"cancelled",
                  order_date, trade_date, settle_date, note}],
  official_last_order_date: null | "YYYY-MM-DD",
  nisa_used_this_year: null | number }
```

- 予算と回数から各回の金額を割り振るボタン(端数は最後の回に寄せる)。
- 確認(エラーと警告、画面に出す):
  - 取消以外の金額の合計が予算を超える → エラー。
  - `nisa_used_this_year` + この年に受渡予定の未受渡分 > 2,400,000 → エラー「成長投資枠の年間上限を超えます」。
  - 予定日を過ぎて status が planned → 警告「予定日を過ぎています。注文済みか確かめてください(二重注文に注意)」。
  - 予定日が注文できない日 → 警告と、次に注文できる日。
  - 予定日が年内受渡の最終注文日(公式の日が入っていればそれ、なければ推定)より後 → 警告「受渡が翌年になり、翌年の枠を使う可能性があります」。
  - 同じ日に注文済みの回が 2 つ以上 → 警告。
  - 現在のスコアが前倒しの閾値以上で、未注文の回がある → 情報「前倒しの条件に達しています(判断はご自身で)」。
  - 価格の条件(levels、drop_rule)に届いた → 情報。
- 回ごとに「注文した」「約定した」を記録でき、約定日・受渡日は SBI の画面の値を手で入れる。
- すべて `localStorage`(キー `nbt:v1`)。読み書きは try/catch で包み、使えなくても画面は動く。書き出しは JSON ファイルのダウンロード、読み込みは同じ形のファイル。
- 画面の見方を閉じた状態は同じ設定データの `guide_closed`(真偽値、既定 `false`)に保存する。項目がない従来の保存データも読み込める。

### 6.3 通知(Web Push)

- 設定画面で「通知を有効にする」→ `push.json` の公開鍵で購読する。公開鍵がない場合は、`scripts/setup_push.py` の実行が必要と案内する。iOS はホーム画面に追加した PWA だけで動くことを案内する。
- 「通知の設定をコピー」で次の JSON を作る。金額と計画名は入れない(ラベルは「1回目」などの自動の名前だけ)。

```
{ "v": 1,
  "subscriptions": [<PushSubscription.toJSON()>],
  "rules": {
    "funds": ["<id>", ...],
    "score_at_least": 70 | null,
    "levels": [{"fund_id", "kind": "index"|"nav", "op": "<=", "value"}],
    "drops": [{"fund_id", "kind", "reference_value", "pct"}],
    "dates": [{"fund_id", "date": "YYYY-MM-DD", "label": "2回目", "days_before": [1, 0]}],
    "year_end": {"fund_ids": [...], "days_before": [5, 1]},
    "ml": {"enabled": false, "prob_at_most": 0.4, "valid_only": true}
  } }
```

- 画面に、GitHub の `Settings → Secrets and variables → Actions → New repository secret` に名前 `PUSH_CONFIG` で貼る手順と、そのページへのリンク(`site/app-config.json` の `repo` から作る)を出す。計画を変えたら貼り直しが要るので、最後にコピーした内容のハッシュを覚え、違ったら「通知の設定が古くなっています」と出す。
- `nbt/notify.py`(朝の実行だけ): `PUSH_CONFIG` と `VAPID_PRIVATE_KEY` が環境変数にあるときだけ動く。判定は状態を持たない。
  - スコア、価格の条件、下落率: 最新日に条件を満たし、その前の営業日に満たしていなかったら通知(またぎ)。
  - 日付: JST の今日 = 予定日 − days_before。本文に「注文済みなら不要です」。
  - 年内受渡: 最終注文日(推定)までの残り国内営業日が days_before に入る日。
  - ML: 有効なときだけ、確率が閾値以下にまたいだら。
- 本文の例: 題「買い時シグナル: FANG+」、本文「スコア 82(かなり割安圏)。52週高値から −12.3%。判断と注文はご自身で。」。通知を押すとアプリを開く。
- 送信は pywebpush。VAPID の `sub` は環境変数 `VAPID_SUBJECT`、なければ `site/app-config.json` の `site_url`(メールアドレスを使わない)。TTL 12 時間。
- ログに出すのは成否の 1 行だけ: `notify: ok`(正常。通知を送った日も、条件を 1 つも満たさなかった日も同じ)、`notify: skipped`(Secret がない、または朝の実行でない)、`notify: error`(失敗。終了コード 1)。ルールの数、条件を満たした数、送った数は出さない。
- 失敗したときは、標準エラーに失敗の種類を 1 行ずつ出す(同じ種類は 1 回だけ)。410/404 は `expired`(購読の期限切れ。端末で通知を有効にし直し、`PUSH_CONFIG` を貼り直す)、それ以外は例外の型の名前。購読先の URL、鍵、ラベル、値は出さない。
- `--send` の実行は、Secret があって朝の実行なら、送信の有無にかかわらず 20 秒かけて終える(早く済んだら残りを待つ)。ログの行は、待ったあとにまとめて出す。送信のある日だけ長くかかったり、行の時刻が早かったりすると、通知を送った日が分かるため。`notify: skipped` のときは待たない。
- 残る手がかり: 送信に失敗した日は `notify: error` になるので、その日に条件を満たしたことは分かる。送信に 20 秒を超えてかかった日は、そのぶん長くなる。
- 手元の試験用に `--dry-run <出力ファイル>` で、送る内容をファイルへ書く。環境変数 `GITHUB_ACTIONS=true` のときは `--dry-run` を拒否する。

## 7. ワークフロー

- `ci.yml`: すべての push と PR。Python 3.13 で `pip install -r requirements.txt`、`pytest -q`、Node で `node --test "tests/js/*.test.mjs"`、`python scripts/privacy_check.py`。
- `pages.yml`: `main` への push、`workflow_dispatch`、schedule の 2 本(`30 22 * * 0-4` = 平日 7:30 JST の朝、`30 12 * * 1-5` = 平日 21:30 JST の夜)。権限は `contents: read`、`pages: write`、`id-token: write`。同時実行は 1 つ。手順: checkout → setup-python(pip のキャッシュ)→ install → build → upload-pages-artifact(`site`)→ 10 秒待つ → deploy-pages → 朝の実行だけ notify(`continue-on-error: true`。Secret がなければ何もしない)。build には `VAPID_PUBLIC_KEY` を `vars` から渡す。
  - 成果物の名前は `github-pages-<実行の回数>`(`github.run_attempt`)にし、deploy-pages にも同じ名前を渡す。同じ実行をやり直すと成果物がもう 1 つできるので、名前が同じだと deploy-pages が「複数ある」と止まる。回数を付ければ、失敗した実行をそのままやり直せる。
  - 配備の前に 10 秒待つのは、アップロードの直後に成果物がまだ一覧に出ておらず、deploy-pages が「見つからない」と止まることがあるため。
  - 台帳(4.9): ジョブを 2 つに分ける。`publish`(ビルド、配備、通知)の権限は従来どおりで、リポジトリへは書けない。build の前に、ブランチ `forward-log` を作業フォルダの外へ取り出し(ブランチがなければ空のフォルダ)、build に `--ledger` で渡す。build のあと、台帳のファイル(`*.jsonl`)を成果物 `forward-log-<実行の回数>` として渡す。取り出しと受け渡しの手順は `continue-on-error: true`(失敗しても配備と通知は変えない)。取り出しに失敗した実行では `--ledger` を渡さない。
  - `ledger`(`publish` のあと。`contents: write` を持つのはこのジョブだけ): 成果物を受け取り、`forward-log` を取り出し直して、受け取ったファイルを写し、commit して push する(ブランチがなければ作る)。すでにあるファイルの内容が、受け取ったファイルの先頭と 1 バイトでも違えば保存しない(足すだけ、を保存の段でも確かめる)。このジョブは checkout も pip もせず、依存パッケージのコードを動かさない(書き込みのトークンを、ビルドのコードと同じジョブに置かない)。`GITHUB_TOKEN` による push は、ほかのワークフローを起動しない。
  - `--explore` は Actions で使わない。
- 使う Actions: `actions/checkout@v5`、`actions/setup-python@v6`、`actions/setup-node@v5`、`actions/configure-pages@v5`、`actions/upload-pages-artifact@v4`、`actions/deploy-pages@v4`、`actions/upload-artifact@v7`、`actions/download-artifact@v8`。
